# 審查流程重新上架：實作前完成度稽核

本文件用來檢查 `review-workflow-relaunch-goal.md` 是否已涵蓋原定目標。它不是程式修改清單，也不授權直接修改現有 APP、GAS、Supabase 或 Google 工作清單。

## 一、稽核結論

目前已達「可以開始實作前的資料契約、schema、mapping 與 prototype 設計」的程度；尚未達「可以直接切換正式資料與全面上線」的程度。

原因不是流程架構缺漏，而是仍有一項主狀態呈現規則需要最後確認：

> 已選定工作流但尚未指派工作者時，`T_State/H_State` 是否留白，另以 `AssignmentStatus=未指派` 表示。

建議採用：主狀態留白、assignment 狀態為 `未指派`；指派後才進入 `書面標注中` 或 `錄音中`。在此規則確認前，實作階段可以進行資料盤點與模型設計，但不應自行定義工作清單的顯示結果。

## 三、目前可以直接進行的工作

在未完成主狀態顯示確認前，不會改變使用者可見正式資料；但下列工作可安全開始：

1. 對現有 APP、Root GAS、Places GAS 的 payload、欄位與 RPC 呼叫做完整 mapping。
2. 設計 `annotation_cases`、`annotation_versions`、`audio_assessments`、事件與 writeback job 的資料契約。
3. 以地名×語種、音檔×地名×語種為單位建立狀態推導測試案例。
4. 設計校對介面的 queue、權限、草稿續作、退回與核准操作。
5. 設計衛星表單送出草稿、版本鎖定、重送與 server-side validation。
6. 盤點現有 `T_Annotator/H_Annotator` 是否先作相容 alias，不先更動實體表頭。
7. 為既有資料建立只讀導入報告，不直接把舊稿當成新流程核准資料。

## 四、目前不可自行推測的事項

只有下列事項需要使用者或計畫規則最後確認：

1. 已分類但尚未指派時，`T_State/H_State` 的顯示值。

下列事項已按目前討論處理，不應再重複提問：

- `直接標注` 未來統一稱為 `書面標注`，但現在不立即改名。
- `原住民族` 與電話／現場調查同樣走 APP 音檔流程，格式暫按相同標音欄位。
- ADMIN 就是現行助理角色，不另外建立助理角色。
- 審聽員採自取案件與 temporary lock，不人工逐筆派案。
- 校對介面採現有 APP 內獨立入口，不另建第二套登入。
- 已核准後的再次修訂暫不納入第一階段。

## 五、進入實作的判定門檻

當唯一未決事項確認後，新的 Codex session 應依下列順序開始：

1. 先不改功能，建立現況欄位／payload／函數 mapping 表並逐項驗證。
2. 提出新資料表與 migration 草案，只讀審查，不立即套用。
3. 建立狀態推導與音檔有效數量的測試資料矩陣。
4. 以測試資料完成審聽、草稿、校對、核准、回寫失敗重試的垂直切片。
5. 通過 readback、權限、冪等與衝突測試後，才進行既有資料導入與正式切換。
