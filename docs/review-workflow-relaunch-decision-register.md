# 審查流程重新上架：決策登錄

本文件記錄本次規劃階段最後採用的解讀，供新的 Codex session 作為規格優先依據。若未來計畫規則改變，應新增決策而不是回頭覆蓋歷史內容。

## D-001：已分類但尚未指派的主狀態

**決策：**

- `T_State/H_State` 允許空值。
- 已選定工作流但尚未指派工作者時，主狀態留白。
- 另以 `T_AssignmentStatus/H_AssignmentStatus=未指派` 表示指派狀態。
- 指派工作者後，才依工作流進入 `書面標注中` 或 `錄音中`。

**依據：** 使用者先前已明確確認「State允許空值」，並已同意 assignment 狀態使用獨立欄位。

**實作限制：**

- 不得把 `未指派` 寫回 `T_State/H_State`。
- 工作清單 UI 可同時顯示工作流類型、空白主狀態與 assignment 狀態，避免空白被誤解為資料遺失。
- 狀態推導測試必須涵蓋「未分類／未指派」、「已分類／未指派」、「已分類／已指派」三種情況。

## D-002：受訪者代號改為選填，不設兩名錄音人門檻

**決策：**

- 「每個地名 × 語種至少兩筆不同受訪人錄音」維持為**工作原則**，但**不由系統強制**。
- 受訪者代號為選填、預設留空，不阻擋音檔判定、送校對或核准。
- UI 不顯示「需要兩名錄音人」之類的要求提示。

**依據：** 使用者於 2026-08-05 明確指示：「2 名錄音人這個是我們的工作原則，但功能設計上不強制也不用顯示，因為實際情形有點複雜，我不希望這個填寫的要求占去太多時間。」

**影響範圍：** 本決策**推翻** `review-workflow-relaunch-goal.md` 第 5.3 節「至少需要兩筆不同受訪人的不重複錄音」與第 6.2 節第 3 點作為系統強制條件的部分；該兩節應視為工作原則陳述，不是驗收條件。

**實作限制：**

- 受訪者代號只作為稽核參考資料，不得成為任何 gate 的判定依據。
- 不得在前端或 RPC 重新加入 distinct respondent count 的阻擋邏輯。
- `review-workflow-core.js` 的 `summarizeAudioEvidence()` 仍可回傳 `distinctRespondentCount` 供顯示，但不得參與 `audioReady` 計算。

## D-003：草稿共用單一校對資料層，但操作介面分離

**決策：**

- 書面標注（衛星表單）與錄音標注的草稿**進入同一套校對資料層**（`annotation_cases` / `annotation_versions`），不分兩套流程。
- 但 APP 介面**分成兩個工作台**：音檔檢驗工作台與校對工作台，由 `getReviewWorkbenchMode()` 切換。
- 音檔檢驗工作台不顯示校對操作；校對工作台對音檔判定與標音內容唯讀。

**依據：** 使用者於 2026-08-05 確認「書面跟錄音的草稿會跑到同一個校對層」，隨後又指出「錄音檔檢驗、標注草稿跟草稿審查是同一個工作台，或許分開會比較好」。兩者並不衝突：資料層統一，操作面分離。

**實作限制：**

- 不得因為介面分離就複製出第二套 case／version 資料表。
- 衛星表單 Pull 必須經 `submit_satellite_annotation_draft()` 進入同一 case，不得直接回寫工作清單。

## 規格優先順序

1. 使用者已確認的本決策登錄與業務規則。
2. `review-workflow-implementation-gap.md` 的規劃／實作落差對照（記錄實際做出來的東西）。
3. `review-workflow-relaunch-goal.md` 的流程與資料模型。
4. `review-workflow-relaunch-data-model-detail.md` 的欄位、不變量與狀態推導契約。
5. `review-workflow-relaunch-function-matrix.md` 的現況函數定位。
6. `review-workflow-relaunch-readiness-audit.md` 的實作前驗收門檻。

> 注意：第 3–6 項是 2026-08-04 凍結的**實作前規劃**，其後 8/5 的實作在 UI 迭代中偏離了部分規格。凡規劃文件與實際程式不一致者，以本決策登錄與落差對照為準，不得逕自依規劃文件「修正」已上線行為。
